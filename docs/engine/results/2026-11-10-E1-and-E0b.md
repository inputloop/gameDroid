# E1 and E0b: a virtio disk over PCI, and the Android kernel, on bvmm

Date: 2026-11-10. Confidence: live-verified, read from CI job logs.
bContain branch `claude/gifted-ramanujan-i2r9yh` at d2a0b5d.

## E1: PCI bus, virtio-pci, virtio-blk. PASS on KVM and WHP

Run: https://github.com/inputloop/gameDroid/actions/runs/42900953163

A Linux 6.12 kernel on bvmm, on both hypervisors:

- found the PCI bus through configuration mechanism #1 and listed the host
  bridge (8086:1237) and one virtio block device (1af4:1042);
- accepted the memory BARs bvmm assigned;
- bound `virtio-pci` and `virtio_blk`, and reported `/dev/vda` as 131072
  sectors (the 64 MiB the host file has);
- read the 14 bytes the host had written at the start of the disk;
- wrote 17 bytes at sector 8, which the host then read back from the file;
- took its interrupts through MSI-X (4 on the request queue's vector).

That exercises every new piece end to end: config space, BAR decoding, the
virtio-pci capability layout, feature negotiation, the virtqueue, the block
device, and MSI delivery on KVM (`KVM_SIGNAL_MSI`) and on WHP (decoded to a
local APIC interrupt). It passed on the first run against a real kernel.

Not covered: several disks, large or concurrent I/O, flush under load,
read-only disks against a real kernel (unit-tested only), and more than one
vCPU taking the interrupts.

## E0b: the stock Android kernel boots on bvmm. PASS, with one defect on WHP

Run: https://github.com/inputloop/gameDroid/actions/runs/42900855102

The kernel taken from the stock Android 17 image
(6.12.74-android16-6, sha256 b28decce...) boots on bvmm on both hypervisors
and runs a container to completion:

    Linux run-2392 6.12.74-android16-6-g3ec022196c4e-ab15076761 #1 SMP PREEMPT ... x86_64 Linux

Two things learned:

1. **It needs to be asked for a serial port.** The first run printed nothing
   and exited at once on both hosts. Android's kernel creates no 8250 ports
   unless `8250.nr_uarts=1` is on the command line (Cuttlefish passes exactly
   that). With it, the console works.
2. **On WHP the kernel has no precise clock.** It reports
   `clocksource: Switched to clocksource refined-jiffies` and
   `Unstable clock detected`. On KVM the same kernel uses `kvm-clock`, then
   `tsc`. This is the risk predicted from the missing Hyper-V support: without
   Hyper-V enlightenments and without a PIT or HPET to calibrate against, the
   kernel never learns the TSC frequency and falls back to counting timer
   ticks. The system runs, but time is coarse, which would hurt frame pacing
   and anything that measures short intervals.

   The log extract starts after the calibration messages, so exactly how the
   tick itself was calibrated is not shown.

The fix planned (milestone E0c): bvmm measures the host TSC frequency and
gives it to the guest, first through the `tsc_early_khz=` kernel argument,
and checks that the guest then reports `clocksource: Switched to clocksource
tsc`.

Limit of this evidence, as before: both CI hosts are AMD and nested.
