## What was built

**In the engine (bContain, `crates/bvmm`):**

- `virtio/net.rs`: a network card (virtio-net). It only carries frames.
- `net/nat.rs`: a private network for the guest with the host's internet
  behind it, made entirely from ordinary host sockets. No driver, no
  administrator rights, no change to the host's network; the host's
  firewall and VPN apply to the guest as to any program.
  - The guest gets 10.0.2.15 by DHCP; the gateway is 10.0.2.2 and the name
    server 10.0.2.3.
  - TCP is ended by a TCP/IP stack (smoltcp) and carried over a host
    `TcpStream`. UDP goes through a host `UdpSocket` per guest port. Names
    are answered with the host's own resolver.
  - IPv4 only. The guest cannot reach the host's loopback services and
    cannot be reached from outside.
- 12 unit tests, with a second TCP/IP stack standing in for the guest:
  700 KB echoed byte for byte, a refused connection refused for the guest
  too, UDP out and back, DHCP, name lookups, ping to the gateway.
- `BVMM_NET_TRACE=1` prints lookups and connections.

**In gameDroid:** three network cards, because the stock image gives cards
roles by position:

| Card | Android's name | The image's role for it | gameDroid connects it to |
|---|---|---|---|
| 1st | `buried_eth0` | The mobile-data modem | Nothing (no modem is emulated) |
| 2nd | `eth1` | Ethernet, marked a restricted network that apps are not given | Nothing |
| 3rd | `buried_eth2`, under `wlan0` | Wi-Fi, when booted with `wifi_impl=virt_wifi` | The NAT |

## How it was found, since two guesses were wrong first

1. One card: Android renamed it `buried_eth0` and gave it no address.
2. Two cards: Android tracked `eth1` as Ethernet but never used it. Its
   capabilities lacked "not restricted", so the default request for a
   network did not match.
3. The image's init scripts showed a Wi-Fi mode on a plain card
   (`virt_wifi`). With the boot setting and a third card, the image's
   helper `setup_wifi` crashed: its source reads `ro.boot.wifi_mac_prefix`
   as a number and aborts on an empty string. Setting
   `androidboot.wifi_mac_prefix` fixed that.
4. The helper then failed differently on some boots: it runs once, and when
   it runs before the `virt_wifi` kernel module has loaded it cannot create
   `wlan0`. This race is inside the stock image. gameDroid creates `wlan0`
   itself after boot if it is missing, then turns Wi-Fi on and joins the
   network.

## Limits

- **IPv4 only.**
- **No incoming connections**, so nothing in Android can act as a server
  reachable from the host or the LAN. This also means adb over the network
  is not available yet.
- **Ping goes no further than the gateway.** Games that measure latency
  with ICMP will see none; most use UDP or TCP.
- **Speed is unmeasured.** The card offers no offloads and every packet
  crosses a userspace TCP/IP stack. Enough for games' traffic by
  expectation, not by measurement.
- **The first two cards are dead weight** kept only to give the third its
  role. Mobile data shows as absent.
- A test tool run from the serial shell (`nc`) could not look names up,
  though Android itself could. That is the shell's environment, not the
  network, and was not chased further.
